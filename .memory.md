## Project Context

### What This Project Does
**AgenticAI - .NET 10 Template Edition** - A framework for building reliable AI workflows in C# using **Railway-Oriented Programming**, **Clean Architecture**, and **agentic primitives** for context engineering.

This is a **template repository** designed to guide .NET development with GitHub Copilot using proven patterns for:
- Domain-driven design with clean architecture
- Railway-Oriented Programming for error handling (Result<T> pattern)
- Agentic AI primitives (instructions, prompts, chatmodes, specs, memory)
- Test-driven development with xUnit
- Functional programming in C# 13.0

### Important Patterns

#### Pattern 1: Railway-Oriented Programming (ROP) with Result<T>
```csharp
// Instead of try/catch for expected failures, use Result<T>
public Result<User> GetUser(string userId)
{
    if (string.IsNullOrEmpty(userId))
        return Result.Failure<User>("User ID is required");
    
    var user = _repository.Find(userId);
    return user is not null 
        ? Result.Success(user)
        : Result.Failure<User>("User not found");
}

// Chain operations with Map/Bind
public async Task<Result> CreateUserWithProfile(CreateUserRequest request)
{
    return await Result.Success(request)
        .MapAsync(r => User.Create(r.Email, r.Name))
        .BindAsync(user => _repository.AddAsync(user))
        .BindAsync(user => _profileService.CreateProfile(user.Id));
}
```

**Key Rules**:
- Use `Result<T>` for operations that may fail
- Use `MapAsync`/`BindAsync` to chain async operations
- Never use `.Result` or `.Wait()` - always await
- Only throw exceptions for truly exceptional cases

#### Pattern 2: Clean Architecture Layers
```
┌─────────────────────────┐
│   Presentation Layer    │  Controllers, Validators
├─────────────────────────┤
│  Application Layer      │  Handlers, Services, Orchestration
├─────────────────────────┤
│  Business Logic Layer   │  Entities, Domain Services, Specifications
├─────────────────────────┤
│  Data Access Layer      │  Repositories, Entity Framework Core
├─────────────────────────┤
│  Data Layer             │  SQL Server, PostgreSQL
└─────────────────────────┘

Rule: Never depend upward! Lower layers have no knowledge of upper layers.
```

**File Organization**:
```
src/[DomainName]/
├── Entities/              # Domain entities (aggregate roots)
├── ValueObjects/          # Immutable value objects (Email, PhoneNumber, etc.)
├── Repositories/          # IRepository interfaces
├── Services/              # Domain services
├── Handlers/              # Command/Query handlers
├── DTOs/                  # Data transfer objects (C# records)
└── Controllers/           # ASP.NET Core controllers

tests/[DomainName].Tests/
├── Unit/                  # Unit tests for services, entities
├── Integration/           # Integration tests for handlers, repositories
└── Fixtures/              # Test fixtures and common test data
```

#### Pattern 3: TDD Red-Green-Refactor for C# / .NET
```
1. WRITE FAILING TEST (Red)
   - Use xUnit [Fact] or [Theory]
   - Arrange, Act, Assert pattern
   - Run: dotnet test → FAIL ❌
   
2. IMPLEMENT MINIMALLY (Green)
   - Write just enough code to pass
   - Focus on correctness, not elegance
   - Run: dotnet test → PASS ✅
   
3. REFACTOR (Blue)
   - Apply SOLID principles
   - Use Railway-Oriented Programming
   - Extract methods, improve naming
   - Run: dotnet test → STILL PASS ✅
```

- `.chatmode.md` - Role-based expertise (Architect, Developer, Reviewer)
- `.prompt.md` - Orchestrated workflows with validation gates
- `.spec.md` - Implementation blueprints with acceptance criteria

- **Description**: Code requires .NET 10 SDK; if running .NET 9 or earlier, build fails
- **Workaround**: `dotnet --version` to check; install .NET 10 SDK from dotnet.microsoft.com
- **Status**: Expected - template is modern by design

- **Workaround**: `dotnet ef migrations add [MigrationName]` then `dotnet ef database update`
- **Status**: Normal EF Core workflow

## Successful Implementations

### Implementation 1: Railway-Oriented Programming Pattern
- **Approach**: Use Result<T> from CSharpFunctionalExtensions for all operations that may fail
- **Files**: Follow `.github/instructions/backend.instructions.md`
- **Lessons**:
  - Eliminates try/catch for expected failures
  - Enables predictable error handling and chaining
  - Type-safe: compiler ensures error paths are handled
  - Makes error scenarios explicit in signatures

### Implementation 2: Spec-Driven Domain Development
- **Approach**: Write `.spec.md` before implementation; let spec guide tests and code
- **Files**: `docs/specs/[feature].spec.md` → `src/[Domain]/` + `tests/[Domain].Tests/`
- **Lessons**:
  - Clear acceptance criteria prevent scope creep
  - Tests directly map to spec requirements
  - Easier handoff between Architect → Developer → Reviewer
  - Enables deterministic, reproducible development

### Implementation 3: Clean Layer Separation
- **Approach**: Strict dependency direction (downward only); each layer has one job
- **Validation**: Run `dotnet build` with analyzer warnings as errors
- **Lessons**:
  - Easy to test (mock lower layers)
  - Easy to swap implementations (e.g., SQL Server ↔ PostgreSQL)
  - Reduces coupling between domains
  - Enables parallel feature development

## Failed Approaches (Don't Repeat)

### Approach 1: Using Exceptions for Expected Failures
- **Problem**: Pollutes call stacks, loses error context, performance overhead from throw/catch
- **Alternative**: Use `Result<T>` pattern for expected failures; only throw for truly exceptional cases
- **Lesson**: Design failures into your types (Result<T>), not your control flow

### Approach 2: Monolithic Project Structure
- **Problem**: Large projects become unmaintainable; hard to find code; high coupling
- **Alternative**: Organize by domain/feature; each domain is a separate namespace with clear boundaries
- **Lesson**: "Screaming architecture" - folder structure should reveal intent

### Approach 3: Skipping Integration Tests
- **Problem**: Unit tests pass but system breaks; mocks hide real issues with EF Core, databases, APIs
- **Alternative**: Include both unit tests (mocked dependencies) and integration tests (real database)
- **Lesson**: You need both layers - unit tests for speed, integration tests for confidence

## Critical Success Factors

### 🚨 Use Railway-Oriented Programming Correctly
- **Problem**: Returning `null` or throwing exceptions for expected failures
- **Rule**: All operations that may fail return `Result<T>` or `Result`
- **Check**: Compiler should enforce: if something might fail, signature must show Result<T>
- **Example**: ✅ `Result<User> GetUser(string id)` vs ❌ `User GetUser(string id)` (hides possibility of failure)

### 🚨 Tests Must Verify Behavior, Not Just Existence
- Test passing ≠ Software working
- ❌ **Bad test**: `Assert.NotNull(user)` - only checks object exists
- ✅ **Good test**: `Assert.Equal("test@example.com", user.Email)` - verifies actual behavior
- ✅ **Good test for failures**: `Assert.True(result.IsFailure)` AND `Assert.Contains("required", result.Error)`
- If the feature would fail in production but tests pass, tests are insufficient

### 🚨 async/await Must Be Used Correctly
- Rule: All I/O operations (database, HTTP, file system) must be async
- ❌ **Bad**: `var user = _repository.GetUser(id);` (blocking, deadlock risk)
- ✅ **Good**: `var user = await _repository.GetUserAsync(id);`
- Never use `.Result` or `.Wait()` - use `await` in async methods
- Mark all I/O-bound methods as `async Task<T>` or `async Task`

### 🚨 Software Must Actually Run and Be Tested Manually
- `dotnet build` passes ≠ software works
- `dotnet test` passes ≠ feature works
- **Before claiming done**:
  1. Run the application: `dotnet run` or start in debugger
  2. Test the feature manually (user perspective)
  3. Check console/logs - must be CLEAN (no unhandled exceptions)
  4. Test error cases - what if invalid input? Deleted record? Network timeout?
- If real execution fails → Return to implementation phase (design was incomplete)

### 🚨 Code Analysis Must Pass With Zero Violations
- `TreatWarningsAsErrors = true` in project file
- Run: `dotnet build` - must show zero warnings
- Analyzers: SonarAnalyzer.CSharp, Microsoft.CodeAnalysis.NetAnalyzers, Meziantou.Analyzer
- All three must approve the code - don't suppress warnings, fix them
- Warnings catch real bugs early

### 🚨 Minimum 80% Code Coverage
- Coverage ≠ Quality, but low coverage = definitely missing tests
- Focus on: Business logic (domains, entities), Error cases, Edge cases
- Don't waste time testing getters/setters
- Prioritize: Handlers (50% coverage), Services (80% coverage), Entities (90% coverage)

### 🚨 XML Documentation & Nullable Reference Types
- All public APIs must have XML doc comments (`/// <summary>`, `/// <param>`, `/// <returns>`)
- Enable `#nullable enable` at file top or project-wide
- Compiler enforces: if a parameter/return might be null, must be nullable (`string?`)
- This prevents `NullReferenceException` at compile time

### 🚨 Code Analysis Must Pass With Zero Violations
- `TreatWarningsAsErrors = true` in project file
- Run: `dotnet build` - must show zero warnings
- Analyzers: SonarAnalyzer.CSharp, Microsoft.CodeAnalysis.NetAnalyzers, Meziantou.Analyzer
- All three must approve the code - don't suppress warnings, fix them
- Warnings catch real bugs early

### 🚨 Minimum 80% Code Coverage
- Coverage ≠ Quality, but low coverage = definitely missing tests
- Focus on: Business logic (domains, entities), Error cases, Edge cases
- Don't waste time testing getters/setters
- Prioritize: Handlers (50% coverage), Services (80% coverage), Entities (90% coverage)
  - Cover edge cases (what if empty/null/extreme values?)
  - Would FAIL if implementation is wrong

## Known Issues & Quirks

### Issue: Test Suite Passes but Software Broken
- **Category**: Testing Quality
- **Description**: All unit tests pass but feature doesn't work when running software
- **Root Cause**: Tests only verify code paths exist, not that behavior is correct
- **How to Prevent**: 
  1. Write behavior-based tests, not existence tests
  2. Manually test in running software (Phase 5)
  3. If Phase 5 fails, improve tests in Phase 2
  4. Update `.memory.md` with missing test cases
- **Status**: Open - being addressed by adding Phase 5 runtime verification
When you need reliable implementation:
1. Create `.spec.md` with acceptance criteria
2. Hand off spec to @developer chatmode in new session
3. Developer implements from spec, not memory
4. Spec becomes source of truth for review

### Pattern: Memory-Driven Test Generation
When writing tests:
1. Check `.memory.md#failed-approaches` - test cases you failed on before
2. Check `.memory.md#known-issues` - edge cases to handle
3. Add new edge cases you discover to the file
4. Next feature benefits from accumulated knowledge

### Pattern: Architecture Consistency
When designing new features:
1. Review `.memory.md#key-architectural-decisions`
2. Check existing patterns in `src/` structure
3. Follow same domain modeling approach
4. Document in `.memory.md#important-patterns` if different
